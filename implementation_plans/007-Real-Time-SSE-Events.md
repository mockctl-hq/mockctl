# 🛠️ IMP-007: Real-Time SSE Events

> **Plan ID:** IMP-007  
> **Version:** 1.1 (Embedded Architecture Shift)  
> **Epic:** Telemetry & Real-Time Dashboards  
> **Status:** 🟢 Approved  
> **Complexity:** High  
> **Target Branch:** `feat/real-time-sse`  

---

## 🎯 1. Objective
Following the completion of the Master Daemon and Project Routing (IMP-006), Mock:ctl requires real-time observability. This implementation will establish a **Server-Sent Events (SSE)** stream (`GET /__mockctl/events`) as per the API Design Guidelines (PKS-027). This stream will push live incoming API request logs and server metrics directly to connected remote clients (e.g., Web-based SaaS Dashboards or Headless CI/CD tools), enabling remote observability. (Note: Local UIs like Flutter will bypass this SSE layer entirely).

## 🏗️ 2. Execution Phases

### 🚧 Phase 1: Core Event Broker (Pub/Sub)
**Target Files:** `internal/runtime/events.go`, `internal/runtime/buffer.go`, `internal/runtime/broker.go`

- **Task 1.1 (Event Definitions):** Define standard event payloads and an explicit `EventType` string (`request_log`, `metric`, `drop_warning`). The `RequestEvent` must include: `sequence_id` (monotonically increasing for drop detection). **CRITICAL (Sequence ID Data Race):** You MUST generate this ID using an `atomic.Int64` counter embedded inside the `EventBroker` struct (NOT a global variable, to comply with PKS-024 No Global State rule, `id.Add(1)`). If you use a standard integer `id++`, 1,000 concurrent requests will cause a fatal Data Race and crash the daemon. If you use `time.Now().UnixNano()`, you will get ID collisions! **CRITICAL (JSON Precision Loss):** JavaScript cannot parse `int64` larger than `2^53 - 1`. You MUST serialize `sequence_id` as a string (`json:"sequence_id,string"`) to prevent silent UI corruption. **CRITICAL (JavaScript Lexicographical Sorting Trap):** If the UI sorts these string IDs, JavaScript evaluates `"10" < "9"` as `true` (lexicographical sorting), causing the UI to scramble the event order after 9 requests! You MUST pad the `sequence_id` string with leading zeros (e.g., `fmt.Sprintf("%016d", id)`) or explicitly document that the frontend MUST cast to `BigInt` before comparison. Also include: `timestamp`, `project_name`, `http_method`, `path`, `status_code`, `latency_ms`, `request_size_bytes`, `response_size_bytes`, `matched_route_id`, `request_headers`, `response_headers`, `query_parameters`, `request_body`, and `response_body` (these MUST be `*RefCountedBuffer` pointers, NOT strings, to safely support zero-allocation passing to asynchronous raw subscribers like BboltPersister), an `is_hijacked` boolean, and **CRITICALLY** four booleans: `is_request_body_truncated`, `is_response_body_truncated`, `is_request_body_base64`, and `is_response_body_base64` so the UI does not crash parsing truncated JSON and can conditionally decode binary payloads. **CRITICAL (Unread Body Paradox):** Add an `is_request_body_ignored` boolean to flag when the mock handler doesn't read the payload. For granular chaos tracking, add `chaos_latency_ms` and `chaos_error_injected`. **CRITICAL (Panic Tracing):** Add a `panic_error` string field so the UI can display fatal crash reasons.
- **Task 1.2 (Narrow Interfaces & Broadcaster):** To comply with the **Narrow Interface Principle** (PKS-024), define distinct `EventPublisher` and `EventSubscriber` interfaces in their respective **consumer packages** (e.g., `RuntimeEngine` and Admin API handlers). Do NOT define these interfaces in the `EventBroker`'s package. Implement a concurrent-safe `EventBroker` struct that satisfies both. **CRITICAL (Event Struct Heap Thrashing):** To achieve Zero-Allocation Architecture, the broker MUST maintain dedicated `sync.Pool`s for `RequestEvent` and `MetricEvent` structs. At 10,000 req/sec, allocating these massive structs on the Heap will destroy the Garbage Collector. Middlewares MUST fetch these structs from the pool, and the Broker's distributor loop MUST return them to the pool once all subscribers (and the persister) have processed them. Use the Fan-Out Pattern instead of locking the subscriber map. **CRITICAL (Single-Thread JSON Bottleneck Fix):** Do NOT encode JSON in the background distributor goroutine; a single goroutine maxes out at ~1,000 req/sec and will drop 99% of traffic under load. The `Publish()` method must accept a pre-encoded JSON `*RefCountedBuffer`. **CRITICAL (Global Firehose Saturation Fix):** Sending 10,000 req/sec to a single Dashboard UI will OOM and crash the client browser. `Publish(event Event, jsonBuf *RefCountedBuffer)` MUST accept BOTH the raw event interface (for metadata routing) and the pre-encoded JSON. The background distributor ONLY handles fast channel Fan-Out. **CRITICAL (Raw Subscriber Data Race):** Because the distributor loops over multiple raw subscribers (e.g., TUI and BboltPersister) and passes them the EXACT SAME `*RequestEvent` pointer fetched from the `sync.Pool`, if TUI finishes and returns the pointer to the pool while the Persister is still batching it, the next request will overwrite the Persister's data! The distributor MUST perform a Shallow Copy of the Event struct (the massive body buffers are safely protected by their own RefCounts) before sending it to each raw subscriber's channel, ensuring each gets an isolated struct copy. It MUST check the subscriber's filter criteria (e.g., `projectName`) before pushing the JSON buffer to their channel. **Crucially, the `Publish()` method itself MUST use a `select` with a `default:` case when sending to `inputChan`**, guaranteeing the Mock API never blocks if the global telemetry buffer fills up. **CRITICAL (Telemetry Overflow Leak):** If `Publish()` drops the event in the `default:` case, it MUST explicitly decrement the event's `RefCountedBuffer`s. Otherwise, every dropped event under heavy load will permanently leak a buffer. **CRITICAL (Lock-Free):** The distributor MUST manage the subscriber map internally via `addChan` and `removeChan` control channels inside its select loop instead of a Mutex, eliminating all lock contention. **CRITICAL (Control Channel Starvation Deadlock):** These control channels MUST be heavily buffered (e.g., `make(chan chan Event, 100)`). If they are unbuffered and the distributor is busy processing 10,000 req/sec from `inputChan`, multiple Dashboard clients disconnecting simultaneously will cause their HTTP handlers' `defer` blocks to permanently hang waiting to send to `removeChan`, leaking goroutines and keeping TCP connections open! **CRITICAL (Post-Shutdown Subscription Deadlock):** If the broker is stopped, the distributor exits. Any subsequent calls to `Subscribe()` or `Unsubscribe()` that do a blocking send (e.g., `addChan <- ch`) will deadlock forever! These methods MUST use a `select` statement listening to both their control channel AND `quitChan` (e.g., `case <-b.quitChan: return nil`) to safely abort. **CRITICAL (Dual-Mode Atomic Count):** The broker MUST maintain TWO separate `atomic.Int32` connection counters: `remoteConnections` (for HTTP SSE clients) and `internalConnections` (for TUI/Bbolt). **CRITICAL (Atomic Counter Underflow):** If a slow client is evicted by the Broker (which calls `Unsubscribe()`), and then the HTTP handler's `defer` block ALSO calls `Unsubscribe()`, the counter will double-decrement, drop below zero, and permanently disable JSON encoding for all future clients! `Unsubscribe()` MUST use a `sync.Once` wrapper per subscriber, or explicitly verify channel existence in the map before decrementing. This allows the API to conditionally skip JSON encoding and Live Metrics if no remote web dashboards are active, saving massive CPU overhead. **CRITICAL (Reference-Counted Memory):** To prevent fatal Use-After-Free data races when `sync.Pool` buffers are passed asynchronously, the HTTP interception buffers MUST be wrapped in a `RefCountedBuffer` struct. **CRITICAL (Zero-Subscriber Memory Leak Fix):** The buffer MUST initialize with `refCount = 1` (owned solely by the HTTP Server). The HTTP Server decrements it upon `Close()`. **CRITICAL (Fan-Out RefCount Race Fix):** The JSON encoded payload MUST ALSO be a `RefCountedBuffer` starting with `refCount = 1` (owned by caller). Inside the Distributor loop, immediately before sending to JSON subscriber channels, it MUST check `if buffer != nil` to prevent a fatal nil pointer dereference (if a remote client connects exactly when traffic was zero) and call `buffer.AddRef(int32(len(jsonSubscribers)))`. After looping over subscribers, the Distributor MUST call `buffer.Decref()` to release the base count. If you set `refCount` to the number of subscribers in the HTTP handler, a subscriber disconnecting before the event reaches the distributor will cause a permanent memory leak! Whichever Goroutine reaches `0` is responsible for safely returning the buffer to its respective pool.
- **Task 1.3 (OOM Prevention & Lifecycle):** To prevent OOM crashes (PKS-026), subscriber channels MUST have a strict buffer limit (e.g., `make(chan *RefCountedBuffer, 100)`). **CRITICAL (Global Telemetry Drop Bug):** The Broker's global `inputChan` MUST ALSO be heavily buffered (e.g., `make(chan *RefCountedBuffer, 1000)`). If you mistakenly instantiate it as unbuffered, `Publish()` will instantly drop 99% of events in its `default:` case. The background distributor MUST use a `select` with a `default:` case to immediately handle events if a subscriber's buffer is full. **CRITICAL (SSE Ring-Buffer Starvation):** If the channel is full, do NOT drop the new event! This will cause slow clients to see only stale data and lose real-time sync. Instead, you MUST implement a "Ring Buffer" eviction policy. **CRITICAL (Dual-Map Recursive Eviction Trap):** Because raw subscribers receive full `Event` structs and JSON subscribers receive `*RefCountedBuffer`s, the Distributor MUST maintain TWO separate, isolated maps (e.g. `rawSubscribers` and `jsonSubscribers`). When evicting from a JSON channel, simply pop and call `old_buf.Decref()`. When evicting from a RAW channel, you MUST pop the `Event` struct and explicitly call `old_event.request_body.Decref()` AND `old_event.response_body.Decref()` (if not nil). Failure to recursively decrement the inner body fields will permanently leak memory on every dropped raw event! *Refinement:* Track dropped counts per subscriber. **CRITICAL (The Drop-Warning Infinite Starvation Loop):** When the channel has space again, do NOT inject a synthetic standalone `drop_warning` event! If you inject an event into the single free slot, you fill the channel again. The *actual* incoming data will be dropped, triggering *another* drop warning, causing an infinite starvation loop where the UI only sees warnings! You MUST inject the dropped count as a metadata property inside the *next successful* event payload (e.g., `event.missed_events = 5`). **CRITICAL (Dual-Channel Interface Paradox):** To prevent forcing native Go UIs to waste CPU on `json.Unmarshal`, the Broker MUST explicitly expose TWO subscription methods: `SubscribeRaw(filterOptions) chan Event` (for TUI, Flutter FFI, Bbolt) and `SubscribeJSON(filterOptions) chan *RefCountedBuffer` (for HTTP SSE clients). Also provide respective Unsubscribe methods. **CRITICAL (Embedded Architecture):** Local interfaces like the TUI (Mock:ctl Studio) and the future Flutter Desktop UI (via a Dart FFI Bridge) will directly invoke `SubscribeRaw()` to read Go Channels natively in memory with zero latency. They will entirely bypass the HTTP SSE network layer (which is reserved exclusively for remote headless clients).
- **Task 1.4 (Graceful Shutdown):** Add a `Stop()` method to signal shutdown. **CRITICAL:** To prevent a fatal `send on closed channel` panic from pending HTTP requests, `Stop()` MUST NOT close `inputChan`. Instead, `Stop()` must send a signal via a dedicated `quitChan` to exit the distributor loop, and use a `sync.WaitGroup` to wait for the distributor Goroutine to fully exit. **CRITICAL (WaitGroup Race Condition):** When initializing the broker, the `wg.Add(1)` MUST be called by the parent thread *BEFORE* spawning the `go distributorLoop()`. If the background goroutine itself calls `wg.Add(1)`, a rapid `Start()` followed by `Stop()` (common in testing) will cause `wg.Wait()` to return immediately before the goroutine starts, causing complete Graceful Shutdown failure! **CRITICAL (Lock-Free Paradox Fix):** Because the subscriber map is an isolated local variable inside the distributor (for lock-free safety), `Stop()` CANNOT iterate over it. The distributor Goroutine ITSELF must iterate over the map and close all subscriber channels right before it returns. **CRITICAL (Shutdown Memory Leak):** When the distributor Goroutine receives the `quitChan` signal, it MUST explicitly drain the `inputChan` in a non-blocking loop and decrement the ref counts of all abandoned events. **CRITICAL (Zombie Publish OOM Leak):** The Broker MUST maintain an `atomic.Bool` `isStopped`. `Stop()` MUST set this to `true` *before* sending the quit signal. `Publish()` MUST explicitly check `if b.isStopped.Load() { event.Decref(); return }`. If omitted, slow HTTP requests finishing *after* shutdown will push events into the dead `inputChan`, permanently leaking `RefCountedBuffer`s and failing memory leak tests! The Go Garbage Collector will safely reclaim `inputChan` (PKS-028).
- **Task 1.5 (Storage Layer Persister):** To comply with **EDL-050** and **PKS-024 Storage Isolation**, telemetry MUST be persisted to the `bbolt` database without polluting the `runtime` package. Create a `TelemetryPersister` struct in the **`internal/storage/`** package (NOT in `runtime`). The Composition Root (`internal/app/app.go`) will instantiate this persister and subscribe it to the `EventBroker` (just like a UI client, but running in the background). It must receive events via its channel and write them to the `telemetry_bucket` in bbolt. **CRITICAL (BBolt Missing Bucket Crash):** The Persister constructor function MUST explicitly execute `db.Update(func(tx *bbolt.Tx) error { _, err := tx.CreateBucketIfNotExists([]byte("telemetry_bucket")); return err })`. If a user runs a fresh install and the background loop attempts to insert telemetry before the bucket is created, BBolt will instantly panic or silently drop all history! **CRITICAL (Async Write Non-Blocking):** The Mock API handlers MUST NEVER block waiting for disk I/O. By making the Persister just another background subscriber to the Broker's Fan-Out, bbolt writes are completely asynchronous. **CRITICAL (Write Batching):** To avoid destroying SSDs and maximizing bbolt performance, the persister MUST NOT open a new `db.Update` transaction for every single event. It MUST accumulate events into a slice and perform a batch insert every `X` milliseconds or when `Y` events are buffered, using a single transaction. **CRITICAL (BBolt Massive Transaction OOM):** The Persister's batch trigger MUST NOT just count events (e.g., `len(batch) >= Y`). If payloads are large (e.g., 2MB each), a batch of 500 events creates a 1GB transaction buffer in RAM, instantly causing an OS OOM crash! You MUST also track cumulative byte size (e.g., `totalBytes >= 5MB`) and force a commit early to prevent transaction buffer explosion. **CRITICAL (BBolt Write Lock Starvation):** BBolt uses a global lock, allowing only ONE write transaction at a time. Under heavy load (10,000 req/s), the Persister will constantly hold the `db.Update()` lock. This will completely starve the Admin API, making it impossible for users to create/edit Mock Endpoints via the Dashboard (they will permanently timeout/hang)! The batch loop MUST implement a `time.Sleep` or adaptive yielding backoff between flushes to guarantee user operations can acquire the write lock. **CRITICAL (BBolt Empty Batch SSD Wear):** Inside the `time.Ticker` block, the batch loop MUST explicitly check `if len(batch) == 0 { continue }` BEFORE opening a `db.Update` transaction. If omitted, the background loop will execute hundreds of thousands of empty transactions per day when the server is idle, wasting CPU cycles and destroying SSD lifespans with unnecessary commit writes! **CRITICAL (Background Goroutine Panic Death):** Because the Persister runs in a background goroutine, if a BBolt disk write panics (e.g., Disk Full), the ENTIRE Master Daemon process will be instantly killed, taking down all Mock APIs! The batching loop MUST have an explicit `defer recover()` block that catches the panic, logs the error, and allows the loop to continue. **CRITICAL (Persister Memory Leak):** After successfully committing the BBolt transaction, the Persister MUST explicitly iterate over the flushed slice and call `.Decref()` on every `request_body` and `response_body` buffer! If omitted, every persisted request will permanently leak RAM until the daemon crashes! **CRITICAL (Storage Explosion Prevention):** BBolt does not auto-compact. If left unchecked, heavy load testing will explode the database size to gigabytes, crashing the OS. The Persister MUST implement a strict Data Retention Policy (e.g., a Ring Buffer mechanism or TTL inside BBolt) enforcing a hard limit of maximum 10,000 persisted requests per project. **CRITICAL (32-bit ARM Mmap Death & Fragmentation Bomb):** BBolt maps the entire database into memory. On 32-bit architectures (like Raspberry Pi, common for Mock servers), the maximum mmap size is ~1-2GB. If telemetry grows beyond ~1GB, the OS will instantly kill the daemon with an OOM `mmap: cannot allocate memory` panic! The Retention Policy MUST enforce a strict byte-size limit (e.g., `< 500MB`). Furthermore, because BBolt deletion causes file fragmentation without shrinking the `.db` file, the system MUST implement a periodic or startup Compaction Routine (reading the DB and writing to a new file) to physically reclaim disk space and prevent a long-term mmap crash after months of uptime. **CRITICAL (OOM Timer Leak):** In the Persister's batching loop, do NOT use `<-time.After(X)` inside the `select` statement. This creates tens of thousands of dead Timer objects per second under load, causing an OOM crash. You MUST use a `time.Ticker` or a reused `timer.Reset()` loop. **CRITICAL (Shutdown Data Loss):** The Persister MUST have its own `Stop()` method (listening to a quit channel). When the Master Daemon shuts down, it MUST call this `Stop()` method to force-flush the final pending RAM batch to the bbolt disk before the process exits, otherwise the last `X` milliseconds of telemetry will be permanently lost!

### 🔌 Phase 2: Engine Telemetry Integration
**Target Files:** `internal/runtime/interceptor.go`, `internal/runtime/telemetry_middleware.go`, `internal/runtime/engine.go`, `internal/runtime/metrics.go`

- **Task 2.1 (Dependency Injection):** Inject the `EventBroker` into the `RuntimeEngine`.
- **Task 2.2 (HTTP Traffic Interception & Truncation):** To prevent `engine.go` from becoming a God Object, implement a standalone `TelemetryMiddleware` in `telemetry_middleware.go`. The `RuntimeEngine` simply chains this middleware in its routing layer. Inside the middleware, intercept incoming requests. **CRITICAL (Slow Reader Invisibility Fix):** If a client uploads a 1GB file over 5 minutes, waiting for the handler to finish will leave the dashboard blind for 5 minutes! The middleware MUST immediately `Publish()` an `EventType: request_started` event containing ONLY the intercepted headers/metadata *BEFORE* passing control to the mock handler. The UI will correlate this with the final `request_completed` event. **CRITICAL (Telemetry Correlation Desync):** You MUST NOT rely on the global atomic `sequence_id` for correlation, because the `request_completed` event will receive a much higher `sequence_id` if other traffic occurs in between! The middleware MUST generate a unique `correlation_id` (e.g., UUID or single atomic fetch) at the start of the request, inject it into the `*TelemetryContext`, and attach the EXACT SAME `correlation_id` to BOTH events. If omitted, the UI will suffer from permanent "Ghost Requests" that never complete. **CRITICAL (Middleware Blindspot Fix):** Because Go's `context.Context` is strictly downward-facing, the mock handler cannot pass `matched_route_id` or `chaos_metrics` back UP to the middleware's `defer` block using standard context values. The middleware MUST construct a mutable pointer (e.g., `*TelemetryContext`) and inject it into the request context *BEFORE* calling `next.ServeHTTP`. The downstream mock handler will mutate this pointer's fields, allowing the middleware's `defer` block to safely read the final metrics. **Crucially, perform a Deep Copy** (using `.Clone()`) of `req.Header` and **CRITICALLY `res.Header`**. **CRITICAL (url.Values Clone Compiler Error):** Go's `url.Values` (`req.URL.Query()`) does NOT have a `.Clone()` method. You MUST explicitly cast it (`http.Header(req.URL.Query()).Clone()`) or manually iterate to copy it, to prevent fatal `concurrent map read/write` panics caused by Go's HTTP server injecting headers after the handler returns. **CRITICAL (PII & Secrets Redaction Latency Fix):** Before attaching headers to the event, you MUST implement a Redaction Engine that scrubs sensitive headers (e.g., Authorization, Cookie, Set-Cookie) replacing their values with "***REDACTED***". **CRITICAL:** Do NOT run heavy Regex on the 1MB JSON body payload synchronously in the HTTP interceptor, as this will introduce a 20-50ms latency penalty destroying the Mock API performance! Full body redaction must only occur asynchronously (or be disabled by default) unless explicitly requested. **CRITICAL (Synchronous Interception Deadlock Fix):** Do NOT pre-read `req.Body` before passing control to the Mock Handler; doing so blocks HTTP streaming payloads forever! Instead, wrap `req.Body` in a custom `io.ReadCloser` (the **Tee-Reader Pattern**) that dynamically intercepts bytes *as the mock handler reads them*, storing up to 1MB into a `sync.Pool` buffer wrapped in a `RefCountedBuffer`. **CRITICAL (Heap Allocation Thrashing Fix):** The `sync.Pool` initializer function MUST pre-allocate the underlying byte slice with maximum capacity (e.g., `bytes.NewBuffer(make([]byte, 0, 1024*1024))`). If you allow it to start at 0 capacity, it will dynamically resize during stream copying, generating 10GB/sec of garbage heap allocations under load, defeating the entire purpose of the pool! **CRITICAL (Dirty Pool Leak):** Whenever you acquire a buffer from `sync.Pool`, you MUST immediately call `buf.Reset()` before writing to it. If omitted, fragments of old payloads (e.g., passwords/tokens) will leak into the new client's telemetry stream! If the limit is reached, set `is_request_body_truncated = true`. **CRITICAL (Telemetry Blindspot):** If `(req.ContentLength > 0 || len(req.TransferEncoding) > 0)` but the Tee-Reader captured `0` bytes by the time the handler returns, set `is_request_body_ignored = true` so the UI can accurately inform the user that their payload was ignored by the server, rather than failing to send. The custom `Close()` method must delegate ONLY to the original `req.Body.Close()`. **CRITICAL (Early Close Use-After-Free):** The Tee-Reader's `Close()` MUST NOT decrement the `RefCountedBuffer`! If a mock handler closes the request body early, decrementing it will return it to the pool while the middleware still needs it, causing a fatal Use-After-Free panic when the middleware's `defer` block tries to publish it! **CRITICAL (Post-Handler Body Drain Memory Corruption):** If a mock handler ignores the request body, Go's HTTP server will automatically drain the unread body AFTER the middleware returns to keep the TCP connection alive. If it reads from the `TeeReader` *after* our `defer` block has already returned the buffer to the `sync.Pool`, the `TeeReader` will blindly overwrite memory currently in use by a completely different request, causing catastrophic data corruption! The `TeeReader` MUST have a `closed atomic.Bool` flag set to `true` by the middleware's `defer` block, and its `Read()` method MUST bypass buffer injection once closed! **CRITICAL (Handler Override Leak):** If a downstream Mock handler mutates `req.Body` (e.g. `req.Body = newBody`), Go's `http.Server` will abandon our custom `ReadCloser`, permanently leaking the pool buffer. The middleware's `defer` block MUST explicitly check `if req.Body != customReadCloser { customReadCloser.Close() }` to guarantee cleanup. To intercept the response, implement a custom `StreamingInterceptorResponseWriter`. It must wrap `Write()` and **CRITICALLY wrap `WriteHeader(statusCode int)`** to accurately capture the HTTP status code. **CRITICAL (The Hijack Panic):** Both the `Write()` and `WriteHeader()` methods MUST explicitly check `if w.is_hijacked { return }`. If a rogue middleware calls `Write` after a WebSocket hijack, Go's HTTP server will throw a fatal `http: response.Write on hijacked connection` panic and instantly crash the server! **CRITICAL (1xx Informational Lockout Bug):** In `WriteHeader`, if `statusCode < 200` (e.g., `100 Continue`), you MUST bypass the `wroteHeader = true` lock! If you lock on 1xx, you will permanently miss the actual final status code (`200 OK`) and silently corrupt the UI telemetry state. **CRITICAL (Telemetry State Corruption):** Go's `http.ResponseWriter` strictly ignores any subsequent calls to `WriteHeader` after the first one. Your interceptor's `WriteHeader` method MUST include an `if w.wroteHeader { return }` check. **CRITICAL (Implicit 200 Panic Lie):** If a mock handler calls `Write()` without explicitly calling `WriteHeader()`, Go implicitly sends a 200 OK. To prevent desync, your interceptor's `Write()` method MUST explicitly check `if !w.wroteHeader` and call `w.WriteHeader(200)` BEFORE writing to the buffer. Failure to do this means a handler panic occurring immediately after a `Write()` will falsely report a 500 error in Telemetry, even though the client already received a 200 OK. It must implement the **Tee-Writer Pattern**—buffering only the first 1MB into a `RefCountedBuffer` (and setting `is_response_body_truncated = true` if exceeded) **WHILE SIMULTANEOUSLY** writing the bytes to the underlying `ResponseWriter` so the client actually receives the network response. **CRITICAL (Write-Boundary Heap Explosion):** When `Write(p []byte)` is called, you MUST NOT blindly pass the entire `p` array to the buffer (e.g., `buf.Write(p)`). If a Mock API writes a massive 10MB file in a single call, Go's `bytes.Buffer` will dynamically resize, allocating 10MB on the Heap and completely bypassing your 1MB OOM protection! You MUST explicitly calculate `remaining := 1MB - buf.Len()`. If `len(p) > remaining`, you MUST strictly slice the array (`buf.Write(p[:remaining])`) before writing. **CRITICAL (Chaotic Goroutine Write-After-Free):** If a chaotic Mock API script spawns a background Goroutine that calls `w.Write()` *after* the main handler returns, the Tee-Writer will intercept it and write to the buffer. Because the middleware's `defer` block already returned the `RefCountedBuffer` to the `sync.Pool`, this delayed write will blindly overwrite memory currently in use by a completely different client! The Interceptor MUST have a `closed atomic.Bool` flag set to `true` when the middleware returns, and its `Write()` method MUST immediately return an error or bypass the buffer if `closed` is true. **Crucially, this interceptor MUST implement `http.Flusher`, `io.ReaderFrom`, `http.Hijacker`, and CRITICALLY `Unwrap() http.ResponseWriter`.** **CRITICAL (Go 1.20 Unwrap Trap):** Go 1.20+ introduced `http.ResponseController`. If a Mock API route uses it to modify timeouts, Go requires the interceptor to have an `Unwrap()` method to access the underlying connection. Omission will cause timeouts to fail and panic! **CRITICAL (Flusher Panic Prevention):** The Interceptor's `Flush()` method MUST use a safe type assertion (`if f, ok := w.ResponseWriter.(http.Flusher); ok { f.Flush() }`) to prevent panics if the underlying writer is a test stub. **CRITICAL (HTTP/2 Feature Detection Panic):** The interceptor's `Hijack()` method MUST explicitly check `if h, ok := w.ResponseWriter.(http.Hijacker); ok` before delegating. Blindly implementing `http.Hijacker` without this check will crash HTTP/2 endpoints, as Go's HTTP/2 server does not support hijacking! If supported and `Hijack()` is called (e.g., for WebSockets), it MUST set an `is_hijacked = true` flag on the interceptor, as the body can no longer be captured. **CRITICAL (WebSocket Telemetry Blindspot):** WebSockets run in infinite loops; thus, the middleware `defer` block will NOT execute until the connection closes hours later. To prevent active WebSockets from being invisible on the Dashboard, your `Hijack()` method MUST immediately construct and `Publish()` a partial `RequestEvent` (with HTTP 101 status) at the exact moment of the hijack. **CRITICAL (Interceptor Hijack Unflushed Buffer Drop):** If the mock handler wrote protocol negotiation bytes (e.g., handshake) BEFORE calling `Hijack()`, those bytes are buffered in the Interceptor but not necessarily sent to the client! When `Hijack()` returns the raw TCP connection to the handler, the Interceptor loses control. Your `Hijack()` method MUST explicitly call `f.Flush()` (if supported) BEFORE delegating to the underlying hijacker. If omitted, those critical bytes are permanently lost, and the WebSocket/gRPC upgrade will mysteriously hang or timeout! **CRITICAL (Hijacked Connection Memory Pinning):** Once a connection is hijacked (e.g., a WebSocket), the handler enters an infinite loop and will NOT return for hours or days! This means the middleware's `defer` block will NOT execute, keeping the 1MB Request and Response `RefCountedBuffer`s permanently pinned in memory, leaking Gigabytes of RAM across thousands of connections! The `Hijack()` method MUST explicitly call `.Decref()` on BOTH the Request and Response buffers immediately before returning the TCP connection, and set a flag so the `defer` block knows they were already cleaned up! **CRITICAL (OS sendfile Zero-Copy Paradox & Blindspot):** If the mock handler triggers `ReadFrom` (e.g. serving a 500MB video), the Interceptor MUST NOT attempt to copy the first 1MB into the buffer. Intercepting it destroys the OS `sendfile` syscall and will crash the server CPU. `ReadFrom` MUST immediately forward the call to the underlying `ResponseWriter` and set an `is_zero_copy = true` flag, intentionally leaving the telemetry response body empty. **CRITICAL:** If the underlying writer does NOT support `io.ReaderFrom` (e.g. gzip middleware), your fallback MUST be `io.Copy(w, src)` (passing the interceptor pointer `w`). If you use `io.Copy(w.ResponseWriter, src)`, you bypass your own `Write()` method, permanently blinding the Telemetry UI to the response body! **CRITICAL (Response Buffer Omission Leak):** Because `ResponseWriter` has no `Close()` method, the middleware's final `defer` block MUST explicitly call `.Decref()` on the Response buffer. If omitted, the buffer will permanently leak on every request.
- **Task 2.3 (Event Dispatch & Panic Recovery):** The middleware must use a `defer` block to synchronously invoke `broker.Publish()` with the final `EventType: request_completed` event when the HTTP handler finishes. **CRITICAL (WebSocket Double-Publish React Crash):** The `defer` block MUST explicitly check `if interceptor.is_hijacked { return }`. The `defer` block MUST explicitly check `if !interceptor.wroteHeader { event.status_code = 200 }` before publishing. **CRITICAL (Panic Bypass & Tracing):** If the mock handler panics, Go's default recovery runs *after* this middleware. Therefore, the `defer` block MUST include a `recover()` to catch panics, populate the event's `panic_error` field with the recovered error string, publish the event, and then call `panic(err)` again to allow Go to print the stack trace. **CRITICAL (Double Panic Server Crash):** The object returned by `recover()` is of type `any` (e.g., `panic(42)`). You MUST NOT blindly type-assert it to `error` (e.g., `err.(error)`). Doing so will trigger a secondary panic inside the recovery block, instantly terminating the daemon without a stack trace! You MUST use `fmt.Sprintf("%v", err)` to safely convert the panic object to a string. **CRITICAL (Panic Status Lie Fix):** Inside the `recover()` block, you MUST ONLY set `event.status_code = 500` IF `!interceptor.wroteHeader`. If true, the handler ITSELF must synchronously encode the JSON (initializing its payload `refCount = 1`), and pass the JSON buffer to `Publish()`, leveraging all CPU cores concurrently. **CRITICAL (JSON Buffer Double-Free Trap):** Once the handler passes the JSON buffer to `Publish()`, ownership is permanently transferred to the Broker. The handler MUST NOT call `defer jsonBuf.Decref()`! If it does, both the handler and the distributor will decrement it, causing a Negative RefCount server panic! If false (e.g., only TUI is running), it passes `nil` for the JSON buffer to save massive CPU waste. **CRITICAL (unsafe.String Memory Corruption Paradox):** Do NOT use `unsafe.String` to populate the `RequestEvent` body fields! Because the `RequestEvent` is fanned out asynchronously to the BboltPersister (which batches writes), the HTTP handler will return and release the buffer back to the `sync.Pool` BEFORE the persister reads it. If you use `unsafe.String`, the persister will read corrupted memory from subsequent requests! You MUST pass the `*RefCountedBuffer` pointer itself into the `RequestEvent` and manage its reference count. When encoding to JSON for HTTP clients, you MUST implement a custom `MarshalJSON` on the `RefCountedBuffer`. **CRITICAL (Slow-Network SSE Disconnect Loop):** If a client is on a slow network (e.g., 500 Kbps), writing a full 1MB JSON payload over SSE will take 16+ seconds, severely violating the 10-second Write Deadline and causing an infinite disconnect/reconnect loop. When creating the SSE JSON payload, the custom MarshalJSON MUST strictly cap the serialized body fields to a smaller limit (e.g., 100KB), appending a `[TRUNCATED FOR SSE]` warning if it exceeds this, while allowing the full 1MB to be passed untouched to the BboltPersister for storage. **CRITICAL (Base64 JSON Trap):** Because the buffer is internally a `[]byte`, Go's `json.Encoder` will blindly Base64-encode ALL payloads by default! You MUST explicitly check `utf8.Valid()`. If it is valid UTF-8 (like JSON/Text), you MUST explicitly format it as a string so the UI can read it naturally. **CRITICAL (Custom MarshalJSON Heap Explosion):** However, you MUST NOT use `json.Marshal(string(b.Bytes()))`! This forces Go to allocate a massive string on the Heap, and then `json.Marshal` allocates a SECOND massive byte slice on the Heap, generating 2MB of instant garbage for every 1MB payload and destroying the Zero-Allocation Architecture! Your custom `MarshalJSON` MUST manually write the opening quote `"`, stream/escape the raw bytes directly without `string()` conversion, and write the closing quote `"`! **CRITICAL (Custom MarshalJSON Protocol Injection):** You MUST NOT blindly stream the raw bytes! If the payload contains raw newlines (`\n`), carriage returns (`\r`), or double quotes (`"`), writing them unescaped creates invalid JSON. Worse, because SSE uses `\n` to delimit events, an unescaped newline will prematurely terminate the SSE message and permanently corrupt the browser's parser! The custom `MarshalJSON` MUST implement an inline byte-scanner that manually escapes these characters to `\\n`, `\\r`, `\\t`, and `\\"` while maintaining zero-allocation. If it is binary (Image/PDF), you MUST encode it as Base64. **CRITICAL (json.Marshal Heap Trap):** Do NOT use `json.Marshal(event)` to encode the event! It will allocate a massive `[]byte` on the Heap, destroying the OOM protection and triggering fatal GC pauses. You MUST use `json.NewEncoder(pooledBuffer).Encode(event)` to stream bytes directly into the pre-allocated memory. **CRITICAL (JSON HTML Escaping Mutilation):** Go's `json.Encoder` automatically escapes HTML (`<`, `>`) into unicode (`\u003c`) by default. If a Mock API returns HTML, the telemetry payload will be maliciously mutated! You MUST explicitly call `encoder.SetEscapeHTML(false)` before encoding to strictly preserve raw payload bytes. **CRITICAL (JSON Newline Parse Error Fix):** Go's `json.NewEncoder` silently appends a trailing `\n` to the encoded byte slice. You MUST explicitly truncate the buffer length by 1 (`buf.Truncate(buf.Len() - 1)`) after encoding. If you fail to do this, the SSE string formatter in Task 3.6 will send `data: {JSON}\n\n\n`, causing 3 newlines which will fatally break strict JavaScript SSE parsers! **CRITICAL (Dangling AddRef Fix):** Do NOT call `.AddRef()` on the Request/Response buffers! Because JSON encoding is now synchronous within the handler, the Request/Response buffers do NOT need to be passed to the background Distributor. They will be safely garbage collected when the handler's `defer` block calls `.Decref()` on the Request and Response buffers ONLY (DO NOT call Decref on the JSON buffer, as ownership is transferred to the Broker)! **CRITICAL:** Do NOT spawn a new Goroutine for `Publish()` (e.g., no `go broker.Publish()`). Since `Publish()` is explicitly designed with a non-blocking `select`, spawning 10,000 Goroutines per second under load is a severe anti-pattern that wastes CPU and RAM.
- **Task 2.4 (Live Metrics Generator & God Object Fix):** To strictly adhere to the Single Responsibility Principle, do NOT place metric generation inside the `EventBroker`. Create a dedicated `MetricsCollector` struct in `metrics.go` that takes an `EventPublisher` as a dependency. Spawn a dedicated Goroutine in the **MetricsCollector** (instantiated once in the Composition Root `internal/app/app.go` and injected, to comply with PKS-024 No Global State rule) that runs on a `time.Ticker` (e.g., every 2s). **CRITICAL (Global GC Paralysis Fix):** A single Mock Daemon can host 1,000+ projects. If the metrics goroutine is inside `RuntimeEngine`, 1,000 goroutines will call `runtime.ReadMemStats` simultaneously, causing massive "Stop The World" GC pauses that paralyze the entire process. The ticker MUST be a singleton. **CRITICAL (Vestigial Deadlock Fix):** Do NOT use complex `0 -> 1` control channels to start/stop the ticker, as rapidly connecting/disconnecting clients will cause unbuffered channel deadlocks. Instead, let the single ticker run continuously. Inside the ticker loop, explicitly check `if publisher.ActiveRemoteConnections() == 0 { continue }`. This avoids deadlocks and consumes virtually zero CPU while idle (since the TelemetryPersister does not need 2s heartbeat metrics). When active, it calls `runtime.ReadMemStats`, constructs a `MetricEvent`, and publishes it. This Goroutine must gracefully exit on `<-ctx.Done()` (PKS-027 & PKS-028).

### 📡 Phase 3: SSE Admin API Endpoint & Middlewares
**Target Files:** `internal/runtime/admin_routes.go`, `internal/runtime/admin_middleware.go`, `internal/runtime/admin_sse.go`

- **Task 3.1 (Strict Header & Localhost Enforcement):** To prevent routing/security conflation, all security checks MUST be isolated in `internal/runtime/admin_middleware.go`. **PKS-027 § 5.2 & § 7** strictly mandates that ALL requests to `/__mockctl/` MUST include the `Authorization` and `Accept-Version` headers. Do NOT modify the security middleware to accept query parameters. The frontend client MUST use a custom streaming HTTP client that can send headers. **CRITICAL (Security):** To comply with PKS-027 Localhost Binding, you MUST implement a middleware that intercepts `req.RemoteAddr`. **CRITICAL (Reverse Proxy Auth Bypass):** Because Mock:ctl will be deployed behind a Reverse Proxy like NGINX (PKS-030), checking ONLY `req.RemoteAddr` is a critical security vulnerability (it will always show NGINX's internal IP). You MUST strictly parse the `X-Forwarded-For` and `X-Real-IP` headers. You must split all IPs in the comma-separated chain, and if ANY single IP is not `127.0.0.1`, `[::1]`, or an RFC 1918 Private Subnet (e.g., `10.x.x.x`, `172.16.x.x`, `192.168.x.x`), it MUST immediately reject the connection with `403 Forbidden`. **CRITICAL (Docker Gateway IP Lockout):** If you strictly enforce ONLY 127.0.0.1, you will permanently block all Dockerized deployments of Mockctl because Docker bridges local traffic through the 172.17.x.x gateway!
- **Task 3.2 (Route Registration & Semaphore Limits):** Map `GET /__mockctl/events` to `handleSSEEvents`. To prevent Goroutine leaks, enforce a hard limit of max 100 concurrent SSE connections globally. **CRITICAL (Global Semaphore Starvation):** Do NOT use a tiny global limit like 5. Because the Master Daemon hosts thousands of projects simultaneously, a tiny global limit will instantly starve other developers, throwing 429 Too Many Requests errors across the entire engineering org! You MUST use a **Buffered Channel Semaphore** (`make(chan struct{}, 100)`) at the start of the handler. **CRITICAL (Semaphore Acquisition Deadlock):** If the semaphore is full, clients blocking on `sem <- struct{}{}` will hang forever if they disconnect (because channel sends ignore HTTP context cancellation)! This leaks goroutines indefinitely! You MUST use a `select` statement: `select { case sem <- struct{}{}: /* acquired */ case <-ctx.Done(): return /* client gave up */ default: return 429 }` to guarantee exactly 100 connections without race conditions or memory leaks. Reject new connections with a 429 status code if the semaphore is full.
- **Task 3.3 (Headers & Configuration):** Once the semaphore is acquired, immediately flush the required SSE headers:
  ```http
  Content-Type: text/event-stream
  Cache-Control: no-cache, no-transform
  X-Accel-Buffering: no
  Access-Control-Allow-Headers: Authorization, Content-Type, Accept-Version
  ```
  **CRITICAL (CDN Buffering Blackhole):** You MUST set `Cache-Control: no-cache, no-transform`. If you omit `no-transform`, enterprise proxies like Cloudflare or AWS ALB will silently intercept and buffer the SSE stream until it reaches 5MB, completely destroying the real-time functionality of the dashboard!
  **CRITICAL (HTTP/2 Protocol Crash):** Do NOT include the `Connection: keep-alive` header! If the Mockctl server is exposed via HTTPS (HTTP/2), sending the `Connection` header is a severe HTTP/2 Protocol Violation that will instantly cause the browser to crash the connection with `PROTOCOL_ERROR`. Go's HTTP/1.1 server handles keep-alive automatically without explicitly needing the header.
  **CRITICAL (CORS Sabotage & Vulnerability Fix):** Do NOT set `Access-Control-Allow-Origin: *`. Browsers strictly reject wildcard origins when an `Authorization` header is present! Furthermore, do NOT blindly echo the client's Origin (`w.Header().Set("Access-Control-Allow-Origin", r.Header.Get("Origin"))`). This causes Arbitrary Origin Reflection, which security scanners flag as a High Risk vulnerability. You MUST implement an Origin Allowlist Validator that verifies the Origin starts with `http://localhost`, `http://127.0.0.1`, or `https://mockctl.com` before echoing it back. If it doesn't match, reject the CORS preflight.
  **CRITICAL (Gzip Buffering Sabotage):** Global compression middleware (e.g., `chi.Compress`) will intercept and buffer the SSE stream, completely breaking real-time behavior. The handler MUST explicitly delete the `Accept-Encoding` header from `req.Header` or use router configuration to strictly exempt `/__mockctl/events` from any Gzip/Deflate middleware.
- **Task 3.4 (Dynamic Write Deadlines & Zombie Peers):** To prevent Slowloris attacks or stuck clients from permanently holding SSE slots, do NOT set an infinite global WriteTimeout (PKS-028 § 14). Instead, use `http.ResponseController(w).SetWriteDeadline(time.Now().Add(10 * time.Second))` dynamically in the stream loop. If a flush blocks for more than 10 seconds, the connection must be immediately closed. **CRITICAL (TCP Half-Open Zombie Leak):** If a mobile client silently drops connection without sending a TCP FIN, the tiny 18-byte heartbeat will easily fit into the OS TCP Kernel buffer without blocking `w.Write()`. The 10-second deadline will NOT trigger. The connection will remain a "Zombie" holding an active slot for 3-5 minutes until the OS TCP Keep-Alive kills it. Ensure the semaphore limit in Task 3.2 is high enough (e.g., 20) to absorb these temporary zombie leaks without paralyzing the dashboard.
- **Task 3.5 (Preflights & Strict JSON Format):** Ensure that `OPTIONS` CORS preflight requests immediately return `204 No Content` and bypass the stream loop. **CRITICAL (CORS Preflight Sabotage):** Before returning `204`, the `OPTIONS` bypass handler MUST explicitly write the `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, and `Access-Control-Allow-Headers` headers. **CRITICAL (CORS CSRF Security Vulnerability):** Do NOT use `*` for the Origin! If you blindly echo any origin, a malicious public website can connect to `127.0.0.1:8080` via the user's browser and silently steal all local mock telemetry. You MUST dynamically read the `Origin` header and strictly verify it against `localhost`, `127.0.0.1`, or RFC 1918 Private Subnets before echoing it back! If you return 204 without these headers, the browser will instantly reject the preflight and completely block the SSE connection! **CRITICAL (CORS Deadlock Prevention):** Browsers NEVER send `Authorization` headers in `OPTIONS` preflight requests. If Auth runs first, it will reject the preflight with 403 Forbidden, permanently breaking SSE for Web UI clients. - **Task 3.6 (Stream Loop & Heartbeat Pings):** At the absolute beginning of the handler, BEFORE acquiring the semaphore, you MUST check `f, ok := w.(http.Flusher)`. If `!ok`, immediately return a 500 status (Streaming Unsupported). **CRITICAL (Accept Header Thread Exhaustion):** You MUST explicitly verify that the client sent the `Accept: text/event-stream` header. If missing, immediately return `406 Not Acceptable`. **CRITICAL (Browser Rejection & Nginx Sabotage):** You MUST explicitly set three HTTP headers before writing any data: `Content-Type: text/event-stream` (otherwise the browser's EventSource will fatally crash), `Cache-Control: no-cache`, and **CRITICALLY** `X-Accel-Buffering: no` (otherwise Nginx/AWS proxies will buffer the stream and completely destroy real-time UI blinking animations). **CRITICAL (Infinite Buffer Fix):** If you fail to check this and enter the stream loop, the SSE data will silently accumulate in the HTTP server's memory indefinitely until the 10-second timeout kills it, making real-time telemetry physically impossible! Flush using the `f.Flush()` method. **CRITICAL (Memory Pool Returns):** After writing the `msg` (which is a `RefCountedBuffer` containing the JSON payload) to the network, the handler MUST decrement its ref count, returning it to the JSON `sync.Pool` if 0. **CRITICAL (Network Block Prevention):** You MUST explicitly check the error returned by `w.Write()`. **CRITICAL (Reverse Proxy Disconnect Hang):** If deployed behind a reverse proxy (e.g., Nginx), client disconnects do NOT always trigger `r.Context().Done()` immediately. The SSE loop MUST NOT blindly block on `w.Write()` or `f.Flush()`. You MUST wrap the write operation with a write deadline (`http.ResponseController(w).SetWriteDeadline(time.Now().Add(2 * time.Second))`), otherwise proxy buffering will cause the Goroutine to permanently hang and leak memory on every disconnect! **CRITICAL (Compiler Panic Fix):** Do NOT attempt to check the error returned by `f.Flush()`!

# 🛠️ IMP-007: Real-Time SSE Events

> **Plan ID:** IMP-007  
> **Epic:** Telemetry & Real-Time Dashboards  
> **Status:** 🟡 Draft  
> **Complexity:** Medium  
> **Target Branch:** `feat/real-time-sse`  

---

## 🎯 1. Objective
Following the completion of the Master Daemon and Project Routing (IMP-006), Mock:ctl requires real-time observability. This implementation will establish a **Server-Sent Events (SSE)** stream (`GET /__mockctl/events`) as per the API Design Guidelines (PKS-027). This stream will push live incoming API request logs and server metrics directly to connected clients (e.g., the future Flutter Desktop UI), enabling real-time dashboards similar to Charles Proxy or Postman.

## 🏗️ 2. Execution Phases

### 🚧 Phase 1: Core Event Broker (Pub/Sub)
**Target Files:** `internal/runtime/events.go`, `internal/runtime/buffer.go`, `internal/runtime/broker.go`

- **Task 1.1 (Event Definitions):** Define standard event payloads and an explicit `EventType` string (`request_log`, `metric`, `drop_warning`). The `RequestEvent` must include: `sequence_id` (monotonically increasing for drop detection). **CRITICAL (JSON Precision Loss):** JavaScript cannot parse `int64` larger than `2^53 - 1`. You MUST serialize `sequence_id` as a string (`json:"sequence_id,string"`) to prevent silent UI corruption. Also include: `timestamp`, `project_name`, `http_method`, `path`, `status_code`, `latency_ms`, `request_size_bytes`, `response_size_bytes`, `matched_route_id`, `request_headers`, `response_headers`, `query_parameters`, `request_body`, `response_body`, an `is_hijacked` boolean, and **CRITICALLY** two booleans `is_request_body_truncated` and `is_response_body_truncated` so the UI does not crash parsing truncated JSON. **CRITICAL (Unread Body Paradox):** Add an `is_request_body_ignored` boolean to flag when the mock handler doesn't read the payload. For granular chaos tracking, add `chaos_latency_ms` and `chaos_error_injected`. **CRITICAL (Panic Tracing):** Add a `panic_error` string field so the UI can display fatal crash reasons.
- **Task 1.2 (Narrow Interfaces & Broadcaster):** To comply with the **Narrow Interface Principle** (PKS-024), define distinct `EventPublisher` and `EventSubscriber` interfaces in their respective **consumer packages** (e.g., `RuntimeEngine` and Admin API handlers). Do NOT define these interfaces in the `EventBroker`'s package. Implement a concurrent-safe `EventBroker` struct that satisfies both. Use the Fan-Out Pattern instead of locking the subscriber map. **CRITICAL (Single-Thread JSON Bottleneck Fix):** Do NOT encode JSON in the background distributor goroutine; a single goroutine maxes out at ~1,000 req/sec and will drop 99% of traffic under load. The `Publish()` method must accept a pre-encoded JSON `*RefCountedBuffer`. **CRITICAL (Global Firehose Saturation Fix):** Sending 10,000 req/sec to a single Dashboard UI will OOM and crash the client browser. `Publish(event Event, jsonBuf *RefCountedBuffer)` MUST accept BOTH the raw event interface (for metadata routing) and the pre-encoded JSON. The background distributor ONLY handles fast channel Fan-Out. It MUST check the subscriber's filter criteria (e.g., `projectName`) before pushing the JSON buffer to their channel. **Crucially, the `Publish()` method itself MUST use a `select` with a `default:` case when sending to `inputChan`**, guaranteeing the Mock API never blocks if the global telemetry buffer fills up. **CRITICAL (Telemetry Overflow Leak):** If `Publish()` drops the event in the `default:` case, it MUST explicitly decrement the event's `RefCountedBuffer`s. Otherwise, every dropped event under heavy load will permanently leak a buffer. **CRITICAL (Lock-Free):** The distributor MUST manage the subscriber map internally via `addChan` and `removeChan` control channels inside its select loop instead of a Mutex, eliminating all lock contention. **CRITICAL (Post-Shutdown Subscription Deadlock):** If the broker is stopped, the distributor exits. Any subsequent calls to `Subscribe()` or `Unsubscribe()` that do a blocking send (e.g., `addChan <- ch`) will deadlock forever! These methods MUST use a `select` statement listening to both their control channel AND `quitChan` (e.g., `case <-b.quitChan: return nil`) to safely abort. **CRITICAL (Atomic Count):** The broker MUST maintain an `atomic.Int32` connection counter (incremented in Subscribe, decremented in Unsubscribe) to allow other Goroutines to check active connections instantly without blocking on control channels. **CRITICAL (Reference-Counted Memory):** To prevent fatal Use-After-Free data races when `sync.Pool` buffers are passed asynchronously, the HTTP interception buffers MUST be wrapped in a `RefCountedBuffer` struct. **CRITICAL (Zero-Subscriber Memory Leak Fix):** The buffer MUST initialize with `refCount = 1` (owned solely by the HTTP Server). The HTTP Server decrements it upon `Close()`. **CRITICAL (Fan-Out RefCount Race Fix):** The JSON encoded payload MUST ALSO be a `RefCountedBuffer` starting with `refCount = 1` (owned by caller). Inside the Distributor loop, immediately before sending to subscriber channels, it MUST dynamically call `buffer.AddRef(int32(len(subscribers)))`. After looping over subscribers, the Distributor MUST call `buffer.Decref()` to release the base count. If you set `refCount` to the number of subscribers in the HTTP handler, a subscriber disconnecting before the event reaches the distributor will cause a permanent memory leak! Whichever Goroutine reaches `0` is responsible for safely returning the buffer to its respective pool.
- **Task 1.3 (OOM Prevention & Lifecycle):** To prevent OOM crashes (PKS-026), subscriber channels MUST have a strict buffer limit (e.g., `make(chan *RefCountedBuffer, 100)`). **CRITICAL (Global Telemetry Drop Bug):** The Broker's global `inputChan` MUST ALSO be heavily buffered (e.g., `make(chan *RefCountedBuffer, 1000)`). If you mistakenly instantiate it as unbuffered, `Publish()` will instantly drop 99% of events in its `default:` case. The background distributor MUST use a `select` with a `default:` case to immediately handle events if a subscriber's buffer is full. **CRITICAL (SSE Ring-Buffer Starvation):** If the channel is full, do NOT drop the new event! This will cause slow clients to see only stale data and lose real-time sync. Instead, you MUST implement a "Ring Buffer" eviction policy: in the `default:` case, actively `pop` the oldest event from the channel (`<-ch`), explicitly call `old_buf.Decref()` on it to prevent memory leaks, and then successfully push the new event into the channel. *Refinement:* Track dropped counts per subscriber, and when the buffer has space, inject a synthetic `drop_warning` event so the UI knows data was lost. Add `Subscribe(filterOptions) chan *RefCountedBuffer` to allow client-side filtering, and explicitly `Unsubscribe(chan *RefCountedBuffer)`.
- **Task 1.4 (Graceful Shutdown):** Add a `Stop()` method to signal shutdown. **CRITICAL:** To prevent a fatal `send on closed channel` panic from pending HTTP requests, `Stop()` MUST NOT close `inputChan`. Instead, `Stop()` must send a signal via a dedicated `quitChan` to exit the distributor loop, and use a `sync.WaitGroup` to wait for the distributor Goroutine to fully exit. **CRITICAL (Lock-Free Paradox Fix):** Because the subscriber map is an isolated local variable inside the distributor (for lock-free safety), `Stop()` CANNOT iterate over it. The distributor Goroutine ITSELF must iterate over the map and close all subscriber channels right before it returns. **CRITICAL (Shutdown Memory Leak):** When the distributor Goroutine receives the `quitChan` signal, it MUST explicitly drain the `inputChan` in a non-blocking loop and decrement the ref counts of all abandoned events. **CRITICAL (Zombie Publish OOM Leak):** The Broker MUST maintain an `atomic.Bool` `isStopped`. `Stop()` MUST set this to `true` *before* sending the quit signal. `Publish()` MUST explicitly check `if b.isStopped.Load() { event.Decref(); return }`. If omitted, slow HTTP requests finishing *after* shutdown will push events into the dead `inputChan`, permanently leaking `RefCountedBuffer`s and failing memory leak tests! The Go Garbage Collector will safely reclaim `inputChan` (PKS-028).
- **Task 1.5 (Bbolt Background Persister):** To comply with **EDL-050**, telemetry MUST be persisted to the `bbolt` database. Create a `BboltPersister` struct that subscribes to the `EventBroker` (just like a UI client, but running in the background). It must receive events via its channel and write them to the `telemetry_bucket` in bbolt. **CRITICAL (Async Write Non-Blocking):** The Mock API handlers MUST NEVER block waiting for disk I/O. By making the `BboltPersister` just another background subscriber to the Broker's Fan-Out, bbolt writes are completely asynchronous. **CRITICAL (Write Batching):** To avoid destroying SSDs and maximizing bbolt performance, the persister MUST NOT open a new `db.Update` transaction for every single event. It MUST accumulate events into a slice and perform a batch insert every `X` milliseconds or when `Y` events are buffered, using a single transaction.

### 🔌 Phase 2: Engine Telemetry Integration
**Target Files:** `internal/runtime/interceptor.go`, `internal/runtime/telemetry_middleware.go`, `internal/runtime/engine.go`, `internal/runtime/metrics.go`

- **Task 2.1 (Dependency Injection):** Inject the `EventBroker` into the `RuntimeEngine`.
- **Task 2.2 (HTTP Traffic Interception & Truncation):** To prevent `engine.go` from becoming a God Object, implement a standalone `TelemetryMiddleware` in `telemetry_middleware.go`. The `RuntimeEngine` simply chains this middleware in its routing layer. Inside the middleware, intercept incoming requests. **CRITICAL (Slow Reader Invisibility Fix):** If a client uploads a 1GB file over 5 minutes, waiting for the handler to finish will leave the dashboard blind for 5 minutes! The middleware MUST immediately `Publish()` an `EventType: request_started` event containing ONLY the intercepted headers/metadata *BEFORE* passing control to the mock handler. The UI will correlate this with the final `request_completed` event via `sequence_id`. **Crucially, perform a Deep Copy** (using `.Clone()`) of `req.Header`, `req.URL.Query()`, and **CRITICALLY `res.Header`** to prevent fatal `concurrent map read/write` panics caused by Go's HTTP server injecting headers after the handler returns. **CRITICAL (Synchronous Interception Deadlock Fix):** Do NOT pre-read `req.Body` before passing control to the Mock Handler; doing so blocks HTTP streaming payloads forever! Instead, wrap `req.Body` in a custom `io.ReadCloser` (the **Tee-Reader Pattern**) that dynamically intercepts bytes *as the mock handler reads them*, storing up to 1MB into a `sync.Pool` buffer wrapped in a `RefCountedBuffer`. **CRITICAL (Dirty Pool Leak):** Whenever you acquire a buffer from `sync.Pool`, you MUST immediately call `buf.Reset()` before writing to it. If omitted, fragments of old payloads (e.g., passwords/tokens) will leak into the new client's telemetry stream! If the limit is reached, set `is_request_body_truncated = true`. **CRITICAL (Telemetry Blindspot):** If `req.ContentLength > 0` but the Tee-Reader captured `0` bytes by the time the handler returns, set `is_request_body_ignored = true` so the UI can accurately inform the user that their payload was ignored by the server, rather than failing to send. The custom `Close()` method must delegate to the original `req.Body.Close()` **AND** decrement the `RefCountedBuffer` (putting it in the pool if 0). (Do NOT use `io.NopCloser` as it leaks TCP connections if the handler attempts an early close). **CRITICAL (Handler Override Leak):** If a downstream Mock handler mutates `req.Body` (e.g. `req.Body = newBody`), Go's `http.Server` will abandon our custom `ReadCloser`, permanently leaking the pool buffer. The middleware's `defer` block MUST explicitly check `if req.Body != customReadCloser { customReadCloser.Close() }` to guarantee cleanup. To intercept the response, implement a custom `StreamingInterceptorResponseWriter`. It must wrap `Write()` and **CRITICALLY wrap `WriteHeader(statusCode int)`** to accurately capture the HTTP status code. **CRITICAL (The Hijack Panic):** Both the `Write()` and `WriteHeader()` methods MUST explicitly check `if w.is_hijacked { return }`. If a rogue middleware calls `Write` after a WebSocket hijack, Go's HTTP server will throw a fatal `http: response.Write on hijacked connection` panic and instantly crash the server! **CRITICAL (1xx Informational Lockout Bug):** In `WriteHeader`, if `statusCode < 200` (e.g., `100 Continue`), you MUST bypass the `wroteHeader = true` lock! If you lock on 1xx, you will permanently miss the actual final status code (`200 OK`) and silently corrupt the UI telemetry state. **CRITICAL (Telemetry State Corruption):** Go's `http.ResponseWriter` strictly ignores any subsequent calls to `WriteHeader` after the first one. Your interceptor's `WriteHeader` method MUST include an `if w.wroteHeader { return }` check. **CRITICAL (Implicit 200 Panic Lie):** If a mock handler calls `Write()` without explicitly calling `WriteHeader()`, Go implicitly sends a 200 OK. To prevent desync, your interceptor's `Write()` method MUST explicitly check `if !w.wroteHeader` and call `w.WriteHeader(200)` BEFORE writing to the buffer. Failure to do this means a handler panic occurring immediately after a `Write()` will falsely report a 500 error in Telemetry, even though the client already received a 200 OK. It must implement the **Tee-Writer Pattern**—buffering only the first 1MB into a `RefCountedBuffer` (and setting `is_response_body_truncated = true` if exceeded) **WHILE SIMULTANEOUSLY** writing the bytes to the underlying `ResponseWriter` so the client actually receives the network response. **Crucially, this interceptor MUST implement `http.Flusher`, `io.ReaderFrom`, and `http.Hijacker`.** **CRITICAL (Flusher Panic Prevention):** The Interceptor's `Flush()` method MUST use a safe type assertion (`if f, ok := w.ResponseWriter.(http.Flusher); ok { f.Flush() }`) to prevent panics if the underlying writer is a test stub. If `Hijack()` is called (e.g., for WebSockets), it MUST set an `is_hijacked = true` flag on the interceptor, as the response body can no longer be captured. **CRITICAL (WebSocket Telemetry Blindspot):** WebSockets run in infinite loops; thus, the middleware `defer` block will NOT execute until the connection closes hours later. To prevent active WebSockets from being invisible on the Dashboard, your `Hijack()` method MUST immediately construct and `Publish()` a partial `RequestEvent` (with HTTP 101 status) at the exact moment of the hijack. **CRITICAL (OS sendfile Zero-Copy Paradox & Blindspot):** If the mock handler triggers `ReadFrom` (e.g. serving a 500MB video), the Interceptor MUST NOT attempt to copy the first 1MB into the buffer. Intercepting it destroys the OS `sendfile` syscall and will crash the server CPU. `ReadFrom` MUST immediately forward the call to the underlying `ResponseWriter` and set an `is_zero_copy = true` flag, intentionally leaving the telemetry response body empty. **CRITICAL:** If the underlying writer does NOT support `io.ReaderFrom` (e.g. gzip middleware), your fallback MUST be `io.Copy(w, src)` (passing the interceptor pointer `w`). If you use `io.Copy(w.ResponseWriter, src)`, you bypass your own `Write()` method, permanently blinding the Telemetry UI to the response body! **CRITICAL (Response Buffer Omission Leak):** Because `ResponseWriter` has no `Close()` method, the middleware's final `defer` block MUST explicitly call `.Decref()` on the Response buffer. If omitted, the buffer will permanently leak on every request.
- **Task 2.3 (Event Dispatch & Panic Recovery):** The middleware must use a `defer` block to synchronously invoke `broker.Publish()` with the final `EventType: request_completed` event when the HTTP handler finishes. **CRITICAL (Ghost Status Fix):** If the mock handler returned without writing a body, Go will automatically inject a `200 OK` *after* the middleware returns, leaving the Interceptor's status code at `0`. The `defer` block MUST explicitly check `if !interceptor.wroteHeader { event.status_code = 200 }` before publishing. **CRITICAL (Panic Bypass & Tracing):** If the mock handler panics, Go's default recovery runs *after* this middleware. Therefore, the `defer` block MUST include a `recover()` to catch panics, populate the event's `panic_error` field with the recovered error string, publish the event, and then call `panic(err)` again to allow Go to print the stack trace. **CRITICAL (Panic Status Lie Fix):** Inside the `recover()` block, you MUST ONLY set `event.status_code = 500` IF `!interceptor.wroteHeader`. If headers were already flushed to the client before the panic, setting 500 creates a false telemetry state. **CRITICAL (Distributed JSON Encoding):** Before calling `Publish()`, the `defer` block MUST check `if broker.ActiveConnections() > 0`. If true, the handler ITSELF must synchronously encode the JSON (initializing its payload `refCount = 1`), and pass the JSON buffer to `Publish()`, leveraging all CPU cores concurrently. **CRITICAL (1MB String Heap Allocation):** When populating the `request_body` and `response_body` strings in the `RequestEvent`, do NOT use `string(buf.Bytes())`! This will cause a massive 1MB heap allocation on every request, completely destroying the GC protection. You MUST use Go 1.20+ `unsafe.String(unsafe.SliceData(buf.Bytes()), len(buf.Bytes()))` for a zero-allocation cast. **CRITICAL (Binary Payload Destruction Fix):** Before using `unsafe.String`, you MUST explicitly check `utf8.Valid(buf.Bytes())`. If the payload is a binary file (e.g., Image/PDF), `unsafe.String` will produce invalid UTF-8 bytes that `json.NewEncoder` will permanently coerce into Unicode Replacement Characters (`\uFFFD`), destroying the payload forever! For invalid UTF-8 (binary), you MUST encode it as Base64 instead. **CRITICAL (json.Marshal Heap Trap):** Do NOT use `json.Marshal(event)` to encode the event! It will allocate a massive `[]byte` on the Heap, destroying the OOM protection and triggering fatal GC pauses. You MUST use `json.NewEncoder(pooledBuffer).Encode(event)` to stream bytes directly into the pre-allocated memory. **CRITICAL (JSON Newline Parse Error Fix):** Go's `json.NewEncoder` silently appends a trailing `\n` to the encoded byte slice. You MUST explicitly truncate the buffer length by 1 (`buf.Truncate(buf.Len() - 1)`) after encoding. If you fail to do this, the SSE string formatter in Task 3.6 will send `data: {JSON}\n\n\n`, causing 3 newlines which will fatally break strict JavaScript SSE parsers! **CRITICAL (Dangling AddRef Fix):** Do NOT call `.AddRef()` on the Request/Response buffers! Because JSON encoding is now synchronous within the handler, the Request/Response buffers do NOT need to be passed to the background Distributor. They will be safely garbage collected when the handler's `defer` block calls `.Decref()`. **CRITICAL:** Do NOT spawn a new Goroutine for `Publish()` (e.g., no `go broker.Publish()`). Since `Publish()` is explicitly designed with a non-blocking `select`, spawning 10,000 Goroutines per second under load is a severe anti-pattern that wastes CPU and RAM.
- **Task 2.4 (Live Metrics Generator & God Object Fix):** To strictly adhere to the Single Responsibility Principle, do NOT place metric generation inside the `EventBroker`. Create a dedicated `MetricsCollector` struct in `metrics.go` that takes an `EventPublisher` as a dependency. Spawn a dedicated Goroutine in the **GLOBAL `MetricsCollector`** (NOT in the `RuntimeEngine`) that runs on a `time.Ticker` (e.g., every 2s). **CRITICAL (Global GC Paralysis Fix):** A single Mock Daemon can host 1,000+ projects. If the metrics goroutine is inside `RuntimeEngine`, 1,000 goroutines will call `runtime.ReadMemStats` simultaneously, causing massive "Stop The World" GC pauses that paralyze the entire process. The ticker MUST be a singleton. **CRITICAL (Vestigial Deadlock Fix):** Do NOT use complex `0 -> 1` control channels to start/stop the ticker, as rapidly connecting/disconnecting clients will cause unbuffered channel deadlocks. Instead, let the single ticker run continuously. Inside the ticker loop, explicitly check `if publisher.ActiveConnections() == 0 { continue }`. This avoids deadlocks and consumes virtually zero CPU while idle. When active, it calls `runtime.ReadMemStats`, constructs a `MetricEvent`, and publishes it. This Goroutine must gracefully exit on `<-ctx.Done()` (PKS-027 & PKS-028).

### 📡 Phase 3: SSE Admin API Endpoint & Middlewares
**Target Files:** `internal/runtime/admin_routes.go`, `internal/runtime/admin_middleware.go`, `internal/runtime/admin_sse.go`

- **Task 3.1 (Strict Header & Localhost Enforcement):** To prevent routing/security conflation, all security checks MUST be isolated in `internal/runtime/admin_middleware.go`. **PKS-027 § 5.2 & § 7** strictly mandates that ALL requests to `/__mockctl/` MUST include the `Authorization` and `Accept-Version` headers. Do NOT modify the security middleware to accept query parameters. The frontend client MUST use a custom streaming HTTP client that can send headers. **CRITICAL (Security):** To comply with PKS-027 Localhost Binding, you MUST implement a middleware that intercepts `req.RemoteAddr`. **CRITICAL (Reverse Proxy Auth Bypass):** Because Mock:ctl will be deployed behind a Reverse Proxy like NGINX (PKS-030), checking ONLY `req.RemoteAddr` is a critical security vulnerability (it will always show NGINX's internal IP). You MUST strictly parse the `X-Forwarded-For` and `X-Real-IP` headers. You must split all IPs in the comma-separated chain, and if ANY single IP is not `127.0.0.1` or `[::1]`, it MUST immediately reject the connection with `403 Forbidden` to prevent external attackers from spoofing or accessing the Admin API.
- **Task 3.2 (Route Registration & Semaphore Limits):** Map `GET /__mockctl/events` to `handleSSEEvents`. To prevent Goroutine leaks, enforce a hard limit of max 5 concurrent SSE connections globally. **CRITICAL (Race-Free Concurrency):** Do NOT use an atomic counter to check limits, as it causes "Check-Then-Act" race conditions under heavy load. You MUST use a **Buffered Channel Semaphore** (`make(chan struct{}, 5)`) at the start of the handler (`select { case sem <- struct{}{}: defer func() { <-sem }() ... default: return 429 }`) to guarantee exactly 5 connections without race conditions. Reject new connections with a 429 status code if the semaphore is full.
- **Task 3.3 (Headers & Configuration):** Once the semaphore is acquired, immediately flush the required SSE headers:
  ```http
  Content-Type: text/event-stream
  Cache-Control: no-cache, no-transform
  X-Accel-Buffering: no
  Access-Control-Allow-Headers: Authorization, Content-Type, Accept-Version
  ```
  **CRITICAL (CDN Buffering Blackhole):** You MUST set `Cache-Control: no-cache, no-transform`. If you omit `no-transform`, enterprise proxies like Cloudflare or AWS ALB will silently intercept and buffer the SSE stream until it reaches 5MB, completely destroying the real-time functionality of the dashboard!
  **CRITICAL (HTTP/2 Protocol Crash):** Do NOT include the `Connection: keep-alive` header! If the Mockctl server is exposed via HTTPS (HTTP/2), sending the `Connection` header is a severe HTTP/2 Protocol Violation that will instantly cause the browser to crash the connection with `PROTOCOL_ERROR`. Go's HTTP/1.1 server handles keep-alive automatically without explicitly needing the header.
  **CRITICAL (CORS Sabotage):** Do NOT set `Access-Control-Allow-Origin: *`. Browsers strictly reject wildcard origins when an `Authorization` header is present! The handler MUST dynamically echo the client's Origin: `w.Header().Set("Access-Control-Allow-Origin", r.Header.Get("Origin"))`.
  **CRITICAL (Gzip Buffering Sabotage):** Global compression middleware (e.g., `chi.Compress`) will intercept and buffer the SSE stream, completely breaking real-time behavior. The handler MUST explicitly delete the `Accept-Encoding` header from `req.Header` or use router configuration to strictly exempt `/__mockctl/events` from any Gzip/Deflate middleware.
- **Task 3.4 (Dynamic Write Deadlines & Zombie Peers):** To prevent Slowloris attacks or stuck clients from permanently holding SSE slots, do NOT set an infinite global WriteTimeout (PKS-028 § 14). Instead, use `http.ResponseController(w).SetWriteDeadline(time.Now().Add(10 * time.Second))` dynamically in the stream loop. If a flush blocks for more than 10 seconds, the connection must be immediately closed. **CRITICAL (TCP Half-Open Zombie Leak):** If a mobile client silently drops connection without sending a TCP FIN, the tiny 18-byte heartbeat will easily fit into the OS TCP Kernel buffer without blocking `w.Write()`. The 10-second deadline will NOT trigger. The connection will remain a "Zombie" holding an active slot for 3-5 minutes until the OS TCP Keep-Alive kills it. Ensure the semaphore limit in Task 3.2 is high enough (e.g., 20) to absorb these temporary zombie leaks without paralyzing the dashboard.
- **Task 3.5 (Preflights & Strict JSON Format):** Ensure that `OPTIONS` CORS preflight requests immediately return `204 No Content` and bypass the stream loop. **CRITICAL (CORS Preflight Sabotage):** Before returning `204`, the `OPTIONS` bypass handler MUST explicitly write the `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, and `Access-Control-Allow-Headers` headers. If you return 204 without these headers, the browser will instantly reject the preflight and completely block the SSE connection! **CRITICAL (CORS Deadlock Prevention):** Browsers NEVER send `Authorization` headers in `OPTIONS` preflight requests. Therefore, the CORS `OPTIONS` bypass middleware MUST execute *before* the Strict Header Enforcement middleware (Task 3.1). If Auth runs first, it will reject the preflight with 403 Forbidden, permanently breaking SSE for Web UI clients. Initial handshake failures (e.g., bad auth) must return standard `application/json` `DomainError` envelopes containing `{ "code": string, "message": string, "http_status": int }` (PKS-025). Additionally, all SSE data payloads MUST be wrapped in the standard `{"success": true, "data": ...}` envelope format (PKS-027).
- **Task 3.6 (Stream Loop & Heartbeat Pings):** At the absolute beginning of the handler, BEFORE acquiring the semaphore, you MUST check `f, ok := w.(http.Flusher)`. If `!ok`, immediately return a 500 status (Streaming Unsupported). **CRITICAL (Infinite Buffer Fix):** If you fail to check this and enter the stream loop, the SSE data will silently accumulate in the HTTP server's memory indefinitely until the 10-second timeout kills it, making real-time telemetry physically impossible! Once verified, acquire a subscriber channel. Run an infinite `select` loop listening for `<-ctx.Done()` or `<-messageChan`. **CRITICAL (Client Disconnect Leak & Reconnect Deadlock Fix):** When the client disconnects and the handler returns, there may still be up to 100 pending messages in the `messageChan`. The handler MUST use a `defer` block to explicitly release the connection Semaphore (`<-sem` from Task 3.2) **BEFORE** calling `Unsubscribe()`. If `Unsubscribe()` blocks and you haven't released the semaphore, a Browser's instant auto-reconnect will hit a full semaphore, receive a 429 error, and permanently stop attempting to reconnect! After `Unsubscribe()`, you MUST explicitly drain the channel (`for msg := range messageChan { msg.Decref() }`). Failure to drain will permanently leak megabytes of memory on every client disconnect. (The Broker must close the channel upon Unsubscribe to break the drain loop). **CRITICAL (CPU Spike Prevention):** When reading from `messageChan`, you MUST check the channel state (`msg, ok := <-messageChan`). If `!ok` (channel closed during Graceful Shutdown), you MUST immediately `return` to prevent a catastrophic 100% CPU infinite busy-wait loop. Format messages using the explicit event type: `event: <EventType>\ndata: {JSON}\n\n` so the UI can parse distinct logs, metrics, and warnings. Flush using the `f.Flush()` method. **CRITICAL (Memory Pool Returns):** After writing the `msg` (which is a `RefCountedBuffer` containing the JSON payload) to the network, the handler MUST decrement its ref count, returning it to the JSON `sync.Pool` if 0. **CRITICAL (Network Block Prevention):** You MUST explicitly check the error returned by `w.Write()` and `f.Flush()`. If an error occurs (e.g., connection dropped or deadline exceeded), immediately `return`/`break` to terminate the handler. Do NOT rely solely on `<-ctx.Done()` as network delays will cause an infinite busy-wait loop. **CRITICAL (Log Spam Fatigue):** If the network error is `syscall.EPIPE` (Broken Pipe) or `syscall.ECONNRESET` (Connection Reset by Peer), you MUST silently swallow it or log it as DEBUG. A client closing their browser tab is a normal event, not a critical system error. Logging it as ERROR will flood the terminal. To prevent proxy timeouts and power the UI blinking micro-animation, integrate a `time.Ticker` that pushes an `event: heartbeat` with an empty data payload every 2 seconds. **CRITICAL (Kernel Syscall Thrash Fix):** You MUST ONLY call `SetWriteDeadline` (from Task 3.4) inside the 2-second `ticker.C` case block! If you call it on every single flush from `messageChan`, heavy load (50,000 req/sec) will trigger 50,000 OS Kernel Syscalls per second, instantly crashing the server CPU via context-switch thrashing. Adding it to the 2-second ticker reduces syscalls to 0.5/sec while maintaining complete security. **CRITICAL:** Add `defer ticker.Stop()` to prevent Timer Goroutine leaks when the connection closes.

### 🧪 Phase 4: Unit Testing & Verification (PKS-029 Compliant)
**Target Files:** `internal/runtime/broker_test.go`, `internal/runtime/buffer_test.go`, `internal/runtime/interceptor_test.go`, `internal/runtime/admin_handlers_test.go`

- **Task 4.1 (Strict Test Foundation):** All isolated unit tests MUST begin with `t.Parallel()` to ensure race conditions are caught during `go test -race` (PKS-029 § 4.5). **CRITICAL (Termux Compatibility Note):** The `-race` flag is unsupported in the Termux Android environment.

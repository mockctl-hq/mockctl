# 📖 Executive Summary

As defined in EDL-012, Mock:ctl **does not use a physical database** (like SQLite, PostgreSQL, or MongoDB) for serving dynamic mock APIs. 

However, to support future monetization, SaaS scaling, and local user telemetry, Mock:ctl implements a **Hybrid Storage Architecture**. This document defines both the ephemeral In-Memory State Architecture (for API simulation) and the persistent System Architecture (for configuration and user data), detailing how concurrency and data lifecycles are safely managed.

---

# 🎯 Purpose

The objectives of this document are to:
- Define the Hybrid Storage architecture (System Data vs Mock Data).
- Define the structural layout of the in-memory database.
- Establish strict thread-safety and concurrency rules.
- Define the data lifecycle (Initialization, Mutation, Reset).
- Detail how nested RESTful resources are mapped to memory.
- Define the snapshot and restore mechanism.
- Establish operational constraints for the embedded SystemStore (File Locking, Migrations, Compaction).

# 🏛️ 1. Hybrid Storage Architecture (Mock Data vs System Data)

Mock:ctl operates on a strict two-tier database model to separate highly dynamic simulation data from permanent system configurations.

## 1.1 StateStore (The Mock Engine)
The `StateStore` is a purely ephemeral, In-Memory map (RAM). 
- **Purpose:** Fast simulation of OpenAPI endpoints.
- **Data Type:** Dynamic, schema-less JSON (`map[string]any`).
- **Speed:** Nanoseconds. Wiped on shutdown (unless explicitly exported).

## 1.2 SystemStore (The Configuration & Monetization Engine)
The `SystemStore` is a lightweight, embedded physical database located at `~/.mockctl/config.db` (or equivalent OS AppData directory). Because it acts as the foundation for future monetization (SaaS/Desktop), it enforces strict engineering rules:

**A. No-CGO Policy (Technology Selection):**
To ensure seamless cross-compilation for Flutter (Desktop/Android) without requiring complex C-toolchains, Mock:ctl strictly prohibits C-based databases like SQLite. The `SystemStore` MUST use a Pure Go Key-Value engine (e.g., `go.etcd.io/bbolt`).

**B. Data Buckets (Schema Design):**
Data is logically partitioned into strict Key-Value buckets:
- `auth_bucket`: Stores Premium License Keys, JWT Tokens, and User IDs.
- `settings_bucket`: Stores CLI/Desktop user preferences (e.g., default ports, UI themes).
- `telemetry_bucket`: Tracks offline usage metrics (e.g., app launches) to aid in future SaaS pricing models.

**C. Security & Cryptographic Tamper-Proofing (JWT):**
To prevent unauthorized tampering of SaaS features, the `SystemStore` does not store plain license keys. It stores **JSON Web Tokens (JWT)** generated by the Cloud Server. These tokens are signed using Asymmetric Cryptography (e.g., RS256). 
- The local Go binary contains a hardcoded **Public Key**. 
- If a user manually edits the `.db` file to extend the token's Expiry Date, the cryptographic signature is immediately invalidated, and the Go backend will reject the token, locking all premium features. This makes local bypassing mathematically impossible.

**D. Cloud Sync & Offline Lease Expiration:**
To provide the creators with visibility into usage (Active Users, OS metrics) and manage Premium features, the `SystemStore` implements a background synchronization engine. Periodically, local data from the `telemetry_bucket` is synced to a centralized Cloud API (`api.mockctl.com`). 
- **Offline Lease:** The JWT stored in the `auth_bucket` contains a strict expiry date (e.g., 30 Days). A user can operate Mock:ctl completely offline for this duration. Once the 30-day lease expires, the token becomes invalid. The Pro features will remain locked until the system connects to the internet to perform a Cloud Sync and fetch a renewed token.

# 🗺️ 2. Core Data Structure

The mock database is fundamentally a two-dimensional map residing in RAM.

## 2.1 The State Tree

Data is organized into "collections" (tables) and "documents" (rows).

```go
// Conceptual mapping
type MemoryDB struct {
    // map[CollectionName] -> map[DocumentID] -> Payload
    store map[string]map[string]any
}
```

- **CollectionName (string):** Represents the REST resource (e.g., `users`, `posts`).
- **DocumentID (string):** The unique identifier for a specific resource (e.g., `123`, `uuid-5678`).
- **Payload (any):** The parsed JSON payload of the resource, typically a `map[string]any`.

## 2.2 Nested Resources Strategy

REST APIs often have nested relationships (e.g., `GET /users/123/posts/456`).
Mock:ctl does not use deeply nested maps for this. Instead, it flattens relationships using a composite collection key.

**Example Routing:**
- `/users/123` ➔ Collection: `users`, ID: `123`
- `/users/123/posts/456` ➔ Collection: `users/123/posts`, ID: `456`

This "Flat Path" strategy avoids complex recursive lookups and keeps the Go map extremely fast and simple.

# 🚦 3. Concurrency & Thread Safety

Since Mock:ctl is an HTTP server, multiple requests (e.g., 100 simultaneous POSTs) can mutate the state at the exact same millisecond. 

Standard Go maps will throw a fatal `fatal error: concurrent map writes` if not protected.

## 3.1 The Mutex Strategy

The Memory State must be wrapped in a `sync.RWMutex` (Read/Write Mutex).

- **Read Operations (`GET`, `List`):** Use `mu.RLock()`. Multiple requests can read the state simultaneously without blocking each other.
- **Write Operations (`POST`, `PUT`, `PATCH`, `DELETE`):** Use `mu.Lock()`. Only one request can mutate the state at a time. Other reads/writes are temporarily blocked.

## 3.2 Granularity

For Version 1.0, Mock:ctl will use a **Global Lock** strategy (one mutex for the entire database) rather than a per-collection lock. Given that Mock:ctl is a local developer tool (not a production database), the microsecond delay of a global lock is negligible and significantly reduces code complexity.

# 🔄 4. The Data Lifecycle

Data in Mock:ctl is ephemeral but highly controllable.

## 4.1 Phase 1: Initialization
When the server starts, the `StateStore` is completely empty. It relies purely on the `RuntimeEngine` to generate dynamic values on-the-fly via `gofakeit` when a `GET` request is made for an item that doesn't exist yet.

*(Exception: If the user provides static JSON Overrides via the Project Component, those are immediately seeded into the `StateStore` at startup).*

## 4.2 Phase 2: Mutation (Schema-Agnostic)
When a client sends a `POST` or `PUT` request, the payload is parsed and saved into the `StateStore`. 
**Validation Boundary:** The `StateStore` is completely **schema-agnostic**. It blindly accepts the `map[string]any` provided to it. All OpenAPI validation (checking types, missing fields, enums) is strictly the responsibility of the `RuntimeEngine` *before* the `Insert` method is called.
**Auto-Timestamps:** If the target OpenAPI schema contains fields named `createdAt` (on POST) or `updatedAt` (on PUT/PATCH), the database automatically injects the current UTC timestamp into the payload before saving.

## 4.3 Phase 3: Partial Updates (PATCH Deep-Merge)
Unlike `PUT` (which replaces an entire document), a `PATCH` request sends incomplete data (e.g., `{"age": 25}`). The `StateStore` implements a recursive **Deep-Merge algorithm** that combines the incoming partial `map[string]any` with the existing `map[string]any` in memory, ensuring no existing data is accidentally deleted.

## 4.4 Phase 4: The Reset Flow
Developers often need a clean slate during automated testing.
Mock:ctl provides an internal reset mechanism (triggered via CLI or a special admin HTTP header/endpoint) that instantly re-initializes the `store` map, wiping all mutations and restoring the server to its startup state.

# 🔑 5. Primary Key (ID) Generation Strategy

Since Mock:ctl lacks a standard SQL database engine with auto-incrementing primary keys, the `StateStore` must dynamically assign DocumentIDs when a client submits a `POST` request.

The ID generation strategy follows a specific fallback hierarchy:

1. **Client-Provided ID:** If the incoming JSON payload already contains an `id` field, the `StateStore` will trust and use it as the DocumentID map key.
2. **Schema-Aware Auto-Increment:** If the OpenAPI schema explicitly types the primary key as an `integer`, the `StateStore` will maintain an internal atomic counter for that collection (e.g., `1, 2, 3...`) and assign the next integer.
3. **UUIDv4 (Default Fallback):** If no ID is provided in the payload and the schema specifies a `string` (or lacks an explicit type), the `StateStore` will generate a random UUIDv4 (via `gofakeit`) and inject it into the payload before saving.

# 🔍 6. Data Querying & Filtering (No SQL Engine)

Because Mock:ctl lacks a standard relational database engine, it does not have built-in support for `WHERE`, `ORDER BY`, or `LIMIT` clauses. The runtime must handle these manually.

## 6.1 Full Collection Scans & Type Coercion
The in-memory data is indexed exclusively by `DocumentID`. 
If a request queries by another field (e.g., `GET /users?age=25`), the `RuntimeEngine` must perform a **Full Collection Scan**. It fetches the entire `map[string]any` for that collection, iterates through every document, and manually checks the fields.
**Type Coercion:** Because URL queries are inherently strings (`"25"` or `"true"`), but JSON fields in memory are typed (`int`, `bool`), the querying logic must perform aggressive type coercion before failing a comparison. 
While O(N) iteration is considered slow in production databases, for a local mock server with a few thousand records, Go handles this loop in microseconds.

## 6.2 Pagination & Sorting
Pagination (`?limit=10&page=2`) and Sorting (`?sort=createdAt_desc`) must be executed *after* the full collection scan. 
The runtime converts the resulting map values into a Go slice (`[]map[string]any`), applies a standard `sort.Slice()`, and then returns the requested slice bounds `[startIndex:endIndex]`.

# 📸 7. Snapshot and Restore (Persistence)

Even though there is no embedded SQL database, developers may want to "save" their current mocked state to share with teammates.

## 7.1 JSON Export
The entire `map[string]map[string]any` structure can be serialized into a single `state.json` file. 

## 7.2 Seed Import
Upon starting the CLI (`mockctl start --seed state.json`), the `StateStore` deserializes this JSON file back into memory, allowing developers to instantly spin up a server with complex pre-existing state.

## 7.3 Graceful Shutdown Auto-Save (Data Loss Prevention)
To prevent accidental data loss if a developer spends hours testing via UI and manually mutating the mock data, Mock:ctl catches `SIGINT`/`SIGTERM` (e.g., when the user presses `Ctrl+C`). Before the process exits, the `RuntimeEngine` automatically dumps the current memory map into a `temp-state.json` file in the `.mockctl/` workspace directory.

# ⚙️ 8. Multi-Process File Locking (SystemStore)

Because `SystemStore` uses an embedded database (like `bbolt`), it attempts to acquire an exclusive OS-level file lock on `config.db`. 
If a developer opens two separate terminals and runs `mockctl start` for two different projects, the second instance will crash if this isn't handled correctly.

**The Implementation Strategy:**
1. **Lock Timeout:** The engine must attempt to acquire the database lock with a strict `1-second timeout`.
2. **Read-Only Fallback:** If the lock is denied (meaning another instance is already running), the second instance MUST gracefully fall back to **Read-Only Mode**.
3. **Behavior in Read-Only Mode:** The second instance can successfully read the License Key and Settings to function normally, but it will skip writing to the `telemetry_bucket`. This ensures the developer's workflow is never interrupted by database crashes.

---

# 🔄 9. Schema Migrations & Versioning (SystemStore)

When Mock:ctl updates (e.g., from v1.0 to v2.0), the structure of the `settings_bucket` or `telemetry_bucket` might change. Without a migration strategy, the app will panic or corrupt the user's permanent data.

**The Implementation Strategy:**
1. **Metadata Versioning:** The `SystemStore` must contain a dedicated `metadata_bucket` that stores the current schema version (e.g., `{"db_version": 1}`).
2. **Migration Runner:** On startup, before the HTTP server begins, the engine compares the binary's version against the `db_version`. 
3. **Sequential Upgrades:** If an upgrade is needed, a Go `MigrationRunner` sequentially applies migration functions (e.g., `migrate_v1_to_v2()`) to transform the data safely before normal operations resume.

---

# 🧹 10. Data Compaction & Telemetry Cleanup

Key-Value stores (like `bbolt`) use append-only mechanisms. Even if you delete data, the physical `.db` file size on the user's hard drive never shrinks automatically. If telemetry logs are written daily, the file will eventually bloat to gigabytes.

**The Implementation Strategy:**
1. **Time-To-Live (TTL):** Telemetry records must have an automatic TTL. Any sync logs older than 30 days must be aggressively deleted by a background goroutine.
2. **Hard Size Limit:** If the `config.db` file exceeds a hard limit (e.g., `50MB`), the `SystemStore` will pause all telemetry logging until a successful Cloud Sync clears the backlog.
3. **Periodic Compaction:** The CLI should occasionally run an internal compaction routine (copying valid data to a new `.db` file and replacing the old one) to physically reclaim disk space.

# 🧠 11. Architecture Rationale: Why No Database for Mock Data? (And Future SaaS Scalability)

The decision to use an in-memory map for the `StateStore` (instead of using the `SystemStore` for everything) is intentional and serves two distinct phases of the product.

## 11.1 Local CLI (Version 1.0)
For the free, local developer CLI, an in-memory map provides:
- **Zero-Setup:** No dependencies to install, no binaries to download.
- **Insane Speed:** Reads and writes happen in nanoseconds without disk I/O.
- **Ephemeral State:** Mock data is meant to be mutated during a test and instantly wiped clean. A RAM map can be reset in `0.0001ms`, whereas SQL requires slow `DELETE` or `DROP` queries.
- **Dynamic JSON (No Schema):** OpenAPI schemas are highly complex. Storing payloads as `map[string]any` allows Mock:ctl to accept *any* JSON structure without worrying about strict SQL columns or ORM migrations.

## 11.2 Future SaaS Scalability
If Mock:ctl is converted into a Cloud SaaS in the future, a single in-memory map per pod will not scale across a distributed Kubernetes cluster (since pod restarts would wipe the state).

However, because Mock:ctl uses a strict `StateStore` Go interface (defined in PKS-024 and PKS-025), the codebase is **future-proof**. 
To support a SaaS model, developers will simply write a new `RedisStateStore` or `PostgresStateStore` that implements the same `Insert/Get/List/Update/Delete` interface. The core `RuntimeEngine` will remain completely unchanged, ensuring a seamless transition from Local CLI to Cloud SaaS.

# 🚧 12. System Limitations & Constraints

Because Mock:ctl Version 1.0 utilizes an in-memory `map` for its `StateStore`, there are specific architectural boundaries that developers must be aware of when writing automated tests against the server.

## 12.1 Memory Management & OOM Protection
To prevent the host machine from running out of memory (OOM Crash) due to infinite loops or aggressive load testing, Mock:ctl imposes a **Hard Limit** on the `StateStore`. 
By default, each collection is limited to **10,000 documents**. If a `POST` request exceeds this limit, the server will return an `HTTP 429 Too Many Requests` or `HTTP 507 Insufficient Storage` error.

## 12.2 Data Isolation (Parallel Testing)
Version 1.0 implements a **Global State**. There are no isolation namespaces or session identifiers. 
This means that if two automated UI tests run in parallel and attempt to mutate the exact same resource, they will experience race conditions at the business-logic level (even though the mutex prevents Go-level data races). Test suites must be run sequentially or use unique mock IDs.

## 12.3 Dumb Relationships (No Cascading Deletes)
In-memory "Flat Paths" do not enforce foreign keys. 
If a user deletes a parent resource (`DELETE /users/123`), the engine **will not** cascade that deletion to nested flat collections (e.g., `/users/123/posts/456` will remain in memory). Developers must explicitly delete nested mock data if their tests require a completely clean tree.

# 📌 Conclusion

The Hybrid Database Design enables Mock:ctl to achieve extreme performance, zero-setup developer experience, and true data ephemerality for Mock APIs, while simultaneously ensuring permanent stability for System Configurations (Monetization & Analytics).
By carefully mapping out concurrency locks, schema-agnostic mutation, flat-path routing, and deep-merge logic, this architecture transforms simple storage components into a robust state engine capable of powering complex backend simulations. 
Furthermore, by establishing strict rules for database migrations, file locking, and data compaction, we have preemptively eliminated the most common operational risks associated with embedded databases, ensuring long-term reliability for end-users.
